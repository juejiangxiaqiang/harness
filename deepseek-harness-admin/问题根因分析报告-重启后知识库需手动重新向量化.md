# 问题根因分析报告：后端重启后知识库必须手动重新向量化

- 分析日期：2026-10-13
- 涉及模块：向量存储配置（SpringAiConfig）、数字员工对话（PreviewChatService）、发布快照展开（ReleaseSnapshotService）、Redis 向量索引、MySQL 元数据
- 结论：**不是启动流程/索引初始化的代码缺陷，而是向量存储被配置为内存型（`local`），向量数据不持久化，重启即丢失；存量向量数据实际完整存在于 Redis，但应用未连接。**

---

## 1. 问题现象

后端重启后，数字员工「笔吧评测室」（id=16）无法回答笔记本价格问题，回复「手册未覆盖」；手动触发该知识库重新向量化后恢复，再次重启再次失效。

### 2.2 关键证据 1：当前后端使用内存向量库

`SpringAiConfig`：

- [SpringAiConfig.java](file:///d:/study/project/AIProject/deepseekHarness/deepseek-harness-admin/deepseek-harness-admin-backend-code/src/main/java/com/harness/admin/config/SpringAiConfig.java#L63-L68) `simpleVectorStore`：`@ConditionalOnProperty(prefix="spring.ai.vectorstore", name="type", havingValue="local", matchIfMissing=true)` → **`type=local` 时创建内存 `SimpleVectorStore`**。
- [SpringAiConfig.java](file:///d:/study/project/AIProject/deepseekHarness/deepseek-harness-admin/deepseek-harness-admin-backend-code/src/main/java/com/harness/admin/config/SpringAiConfig.java#L87-L115) `redisVectorStore`：`@ConditionalOnProperty(..., havingValue="redis")` → **`type=local` 时不创建 Redis 向量库 bean**。

即：当前进程根本不连接 Redis，向量只存在 JVM 堆内，**重启即清空**。

- 抽查 JSON 文档 `embedding` 实际维度 = **1024**（与当前 qwen 模型维度一致，可被当前检索直接复用）。

### 2.4 关键证据 3：Spring AI 2.0.1 启动时不会破坏存量索引

反编译 `spring-ai-redis-store-2.0.1` 的 `RedisVectorStore.afterPropertiesSet()`：

```
if (!this.initializeSchema) return;
if (this.jedisClient.ftList().contains(this.indexName)) return;  // 索引已存在 → 跳过，不 drop/重建
ftCreate(...)  // 仅索引不存在时创建
```

结论：即使切回 `redis` 类型，重启时检测到 `harness_kb_index` 已存在会**安全跳过**，不重建、不丢数据（`FT.INFO` 显示 `hash_indexing_failures=0`）。

## 3. 完整问题链路

```text
后端启动（type=local）
  └─ SpringAiConfig 创建 内存 SimpleVectorStore（RedisVectorStore bean 不创建）
对话：笔吧评测室(id=16) → Skill 8(查询笔记本电脑价格, ACTIVE) → KB 14(笔记本电脑价格金砖版, READY, 6片)
  └─ PreviewChatService.resolveKnowledgeBaseIds() 走发布快照展开，仅查 MySQL（status=READY 成立）
  └─ PreviewChatService.retrieve(kbIds=[14])  → 向量库相似度检索
        └─ 内存向量库为空（重启清空）→ 0 命中
  └─ buildPrompt() 无知识片段 → LLM(qwen3.8-flash) 回复「手册未覆盖」
手动重新向量化
  └─ 解析+切分+嵌入 → 写入内存向量库 → 检索恢复（直到下次重启）
```

故障点：**对话检索命中的向量库是「内存库」，而非存有完整数据的 Redis**。DB 中 `READY` 状态只代表「历史曾向量化成功」，不校验向量数据当前是否可检索，因此重启后 DB 状态与真实向量数据脱节，检索静默空命中。

## 4. 根因结论

- **直接根因**：`SPRING_AI_VECTORSTORE_TYPE=local` 使后端使用内存向量库，向量数据不持久化，每次重启丢失；重启后没有「已存在的向量化数据」可加载。
- **深层原因**：存量向量数据完整保存在 Redis（索引 schema 正确、kb-14 六片 1024 维与当前嵌入模型一致），但 `local` 模式下应用不创建 RedisVectorStore bean、不连接 Redis，导致已持久化的数据被闲置。
- **排除项**：启动流程、向量索引初始化机制、数字员工与知识库关联调用链路均无代码缺陷——Spring AI 2.0.1 对已存在索引安全跳过（证据 2.4）；关联链路正常（证据 2.5）。

## 5. 修复方案建议

### 5.1 首选（最小修复，推荐）

将 `.env` 中向量库类型切回持久化的 Redis：

```env
SPRING_AI_VECTORSTORE_TYPE=redis
```

- 重启后 `redisVectorStore` bean 创建，检测到 `harness_kb_index` 已存在即安全跳过（不重建）；
- 直接复用 Redis 中 kb-14 的 6 片 1024 维向量（维度与当前 qwen 嵌入模型一致），**无需手动重新向量化**；
- 与 [docs/DEPLOYMENT.md](file:///d:/study/project/AIProject/deepseekHarness/deepseek-harness-admin/docs/DEPLOYMENT.md) 中「生产使用 redis」约定一致。

### 5.2 加固（可选）

1. **环境隔离**：dev 用 `local`、生产强制 `redis`，避免误切后出现本问题（如部署脚本校验生产环境不允许 `local`）。
2. **启动健康校验**：启动后对 `READY` 知识库做轻量核对（如 `vectorStore.count(kb_id==x)` 与 `chunk_count` 比对），不一致记录告警，避免检索静默空命中；不建议启动期自动全量重新向量化（外部嵌入服务突发依赖）。
3. **运维文档补充**：在系统测试/运维手册增加「重启后无需重新向量化」的验证步骤，防止再以手动重向量化掩盖配置漂移。

### 5.3 验证方法（需重启后端后执行）

1. 修改 `.env` → 用户重启后端；
2. 再次调用 `POST /api/digital-employees/16/chat`，应直接命中知识库给出价格答案，而非「手册未覆盖」；
3. 再次重启后端，重复第 2 步仍正常（证明向量数据持久化生效）。
