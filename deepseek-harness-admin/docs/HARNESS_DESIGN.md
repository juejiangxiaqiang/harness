# Harness 领域设计

## 1. 核心概念

### 知识库

管理员维护的全局共享业务资料集合。知识库上传后需要经过解析、切分和向量化，并将向量写入向量数据库。知识库包含文件元数据、处理状态和操作审计信息，不属于单个用户。

### Skill

数字员工可使用的能力配置。Skill 描述能力名称、使用说明、输入输出约定和实现配置，并可以关联一个或多个知识库。

### 数字员工

由提示词、模型配置和一个或多个 Skills 组合而成的可运行智能体配置。数字员工不直接维护知识库关联，其可使用的知识库由所选 Skills 间接确定。

### 发布版本

管理员发布的数字员工某一时刻的不可变配置快照。发布版本用于审计、回滚和普通用户侧运行。

## 2. 核心关系

```text
管理员 ──维护── 全局共享知识库
管理员 ──维护── 全局共享 Skill
管理员 ──维护── 全局共享数字员工
Skill N ── N 知识库
数字员工 N ── N Skill
数字员工 1 ── N 发布版本
普通用户 ──使用── 已发布数字员工
```

## 3. 数字员工生命周期

```text
DRAFT → PUBLISHED
  │         │
  └──────→ ARCHIVED
```

- `DRAFT`：可以编辑，尚未对外提供。
- `PUBLISHED`：已完成发布校验，可被使用。
- `ARCHIVED`：历史或停用状态。

## 4. 发布流程

1. 校验当前账号已认证且具有管理员角色。
2. 校验数字员工基础信息。
3. 校验模型配置和系统提示词。
4. 校验关联 Skills 是否存在且可用。
5. 根据 Skills 展开其关联知识库。
6. 校验展开后的知识库均已完成向量化并处于 `READY` 状态。
7. 创建包含 Skill 和知识库引用关系的发布版本快照。
8. 更新数字员工发布状态。
9. 记录发布人、发布时间和版本号。

任何一步失败都不得产生不完整的发布结果。

## 5. 知识库上传状态

```text
UPLOADING → PROCESSING → READY
     │           │          │
     └──────────→ FAILED ←──┘
```

- `UPLOADING`：已创建上传记录，文件仍在处理。
- `PROCESSING`：正在解析、切分、生成向量或写入向量数据库。
- `READY`：向量化处理完成，可以被 Skill 选择。
- `FAILED`：处理失败，需要记录失败原因并支持重新处理。

## 6. 知识库向量化流程

1. 接收并保存原始文件和知识库元数据。
2. 创建知识库处理任务，将状态设置为 `UPLOADING`。
3. 解析文件内容并切分为文档片段。
4. 使用 Spring AI 的 Embedding 能力调用向量模型。
5. 将文档片段、元数据和向量写入向量数据库。
6. 全部片段写入成功后，将知识库状态更新为 `READY`。
7. 任一步骤失败时，将状态更新为 `FAILED` 并记录失败原因。

向量模型和向量数据库必须通过可替换的配置接入，避免业务服务直接依赖具体厂商 SDK。

## 7. 一致性要求

- 发布版本保存完整配置快照，不依赖之后可变的草稿数据。
- 删除或禁用资源后，已发布版本仍可追溯。
- 关联关系创建时必须校验资源存在和状态；管理操作必须校验管理员角色。
- Skill 只能关联 `READY` 状态的知识库。
- 数字员工只能关联 Skill，不能直接写入知识库关联。
- 发布时应根据 Skill 计算实际知识库集合，并保存到发布快照中。
- 资源为全局共享资源，不根据创建人限制读取或关联；创建人、更新人和发布人仅用于审计。
- 普通用户只能使用已发布版本，不得访问管理能力。
- 状态变更应记录操作者和时间。

## 8. 向量化任务治理

- 每次知识库处理对应一个唯一任务 ID。
- 任务使用知识库 ID、原始文件版本和处理配置生成幂等键。
- 相同幂等键的任务不能重复创建或重复写入向量。
- 任务执行前将知识库状态从 `UPLOADING` 更新为 `PROCESSING`。
- 任务成功后才允许更新为 `READY`。
- 任务失败时记录错误原因、失败次数和最后失败时间。
- 重试采用有限次数和指数退避，超过次数后保持 `FAILED`。
- 向量写入应使用稳定的文档片段 ID，重试时执行幂等 upsert。
- 重新处理前清理当前文件版本对应的旧向量，避免旧片段残留。
- 删除知识库时必须同步删除对应向量或标记为不可检索。

**实现说明（与代码一致）**：

- 任务表 `knowledge_base_task` 记录状态（`PENDING/RUNNING/SUCCESS/FAILED`）、重试次数、失败原因与起止时间。
- 幂等键 = `SHA-256(知识库ID + ":" + 文件存储键 + ":" + 任务序号)`，`idempotency_key` 唯一约束兜底并发；任务序号随重处理递增，允许同文件多次重处理，同时以"存在 `PENDING/RUNNING` 活跃任务则拒绝"拦截并发重复。
- 向量片段 ID = `kb-{知识库ID}-{存储键}-{序号}`，同参数重复写入覆盖同 ID 向量（幂等 upsert）。
- 重试默认最多 2 次（共 3 次尝试），退避基准 2 秒指数递增，均通过配置 `harness.vectorization.*` 调整。
- 默认接入本地哈希向量模型与内存向量库（`SimpleVectorStore`，按 `kb_id` 元数据过滤删除）；引入真实厂商 starter 后由 `@ConditionalOnMissingBean` 自动替换，业务代码不绑定厂商。
- Embedding 提供方与向量库类型均可配置：`SPRING_AI_EMBEDDING_PROVIDER=local|openai`（openai 时接入 OpenAI 兼容服务，如阿里云百炼 qwen3）；`SPRING_AI_VECTORSTORE_TYPE=local|redis`（redis 需 RediSearch 模块，索引维度取自 Embedding 模型）。
- 向量清理为 best-effort：首次写入前向量库元数据字段尚未注册/索引不存在时跳过清理（日志 WARN），不阻塞向量化；重复处理同版本文件由稳定片段 ID 覆盖保证幂等。
- 支持的文件解析类型为 `txt/md`；`pdf/docx` 已允许上传但暂不支持解析，进入 `FAILED` 并记录原因。

## 9. 发布快照与回滚

- 每次发布都生成新的不可变版本号。
- 发布快照至少包含系统提示词、模型配置、Skill ID 和版本、实际知识库 ID 和版本、向量模型标识。
- 草稿修改不会改变已发布快照。
- 只有校验成功的版本才能成为当前生效版本。
- 回滚通过选择历史发布版本创建新的生效记录，不修改历史快照。
- 回滚前校验历史版本引用的资源仍存在且可用；若资源不可用，回滚必须失败并记录原因。
- 发布和回滚均记录管理员、时间、版本、结果和失败原因。

**实现说明（与代码一致）**：

- 版本号为基于发布记录总数的递增序号（字符串），记录于 `digital_employee_release.version`。
- 配置快照为 JSON，含 `systemPrompt`、`modelConfig`、`skills`（`skillId`/`skillVersion`）、`knowledgeBases`（`knowledgeBaseId`/`embeddingModel`/`chunkCount`），随记录不可变存储。
- 发布校验失败与回滚前置校验失败均写入 `FAILED` 状态的发布记录并保留失败原因（独立事务，不随异常回滚）。
- 回滚请求携带历史发布记录 ID，仅允许本数字员工的 `SUCCESS` 记录；成功后在历史快照基础上生成新的生效记录并切换当前发布版本。

## 10. 管理端预览对话

管理端在数字员工预览页提供管理员专用的实时对话验证能力（对照 [REQUIREMENTS.md](./REQUIREMENTS.md) 3.8），用于发布前/后核对数字员工回复效果。

### 10.1 能力定位

- 使用方：已认证的管理员，且仅在预览页「预览」页签生效。
- 用途：管理验证用途，不替代普通用户端的运行/对话服务（管理后台边界见 [ARCHITECTURE.md](./ARCHITECTURE.md) 第 8 章）。
- 数据基础：以该数字员工当前配置（系统提示词、模型配置及关联 Skills 展开的 READY 知识库）作为检索与生成的依据。

### 10.2 对话处理流程

1. 管理员在预览页输入问题或点击快捷提问，前端携带 `message`（可选 `conversationId`）调用对话接口（`POST /api/digital-employees/{id}/chat`）。
2. 后端解析或创建会话，并校验会话归属数字员工。
3. 加载数字员工当前配置，按 Skills 展开其关联且为 `READY` 的知识库集合。
4. 将用户问题向量化（复用 `EmbeddingModel`），在 `VectorStore` 中按相似度检索相关文档片段。
5. 将系统提示词、命中的文档片段与用户问题组装为对话上下文，调用聊天模型。
6. 一次性返回完整回复，并将用户问题与回复写入 `preview_message`。

### 10.3 与向量化的关系

- 检索与知识库向量化共用 `EmbeddingModel` 与 `VectorStore` 抽象，不引入新的向量库或模型绑定。
- 仅检索 `READY` 状态且可用的知识库；无可检索知识库时返回明确业务错误，前端可重试。

### 10.4 状态与持久化

- 预览对话为**有状态持久化**能力：会话记录于 `preview_conversation`、消息记录于 `preview_message`。
- 提供会话历史与消息历史查询接口，支撑管理员回看对话。
- 对话内容不进入审计日志；问题与回复仅作为管理验证数据落库。

### 10.5 一致性要求

- 对话接口必须校验 `ADMIN` 角色；普通用户调用返回 `RESOURCE_FORBIDDEN`。
- 检索、组装、生成任一步骤失败均按统一错误码返回且可重试，不产生部分污染数据。
- 对话模型未配置（`CHAT_PROVIDER_NOT_CONFIGURED`）或生成失败（`CHAT_FAILED`）均有明确错误码。
- 对话内容不得写入密码、令牌、API Key 或其它敏感信息到日志与响应。
