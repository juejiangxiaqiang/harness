# 系统测试

> 本文档描述 Harness 管理后台「前端 × 后端」联调阶段的系统测试方案，采用**模拟真实用户完整操作流程**的页面级黑盒测试方法，覆盖需求文档定义的 ≥90% 系统功能，并对「创建数字员工」核心功能实现 100% 覆盖（含子功能、边界条件与异常场景）。
>
> 关联文档：[项目需求](./REQUIREMENTS.md)、[API 约定](./API_SPEC.md)、[测试与验收](./TESTING.md)、[前端开发计划书](./前端开发计划书.md)、[视觉设计](./VISUAL_DESIGN.md)。

## 1. 文档说明

### 1.1 编写目的

1. 为前后端联调阶段提供一套可直接执行的系统测试用例，验证管理后台各功能链路（登录 → 知识库 → Skill → 数字员工 → 发布/预览）在真实浏览器操作下的正确性、一致性与可恢复性。
2. 规范测试执行记录与缺陷反馈流程，保证问题可追溯、可回归、可验收。
3. 为后续回归测试、上线验收提供基线文档。

### 1.2 适用范围

- 适用对象：测试人员、前后端开发人员、验收评审人员。
- 适用阶段：前后端联调阶段、上线前的系统级验收测试。
- 被测系统：`deepseek-harness-admin`（后端）与 `deepseek-harness-admin-frontend-code`（前端管理后台）组成的整体系统。
- 覆盖范围：登录/退出、知识库上传与管理、Skill 创建与管理、数字员工创建/发布/预览、权限与安全边界、异常与错误处理。

### 1.3 术语定义

| 术语 | 含义 |
|---|---|
| 页面级黑盒测试 | 仅通过浏览器对页面进行操作与观察，不接触后端代码与数据库 |
| 全流程点击操作 | 按真实用户路径，通过鼠标/键盘完成从入口到结果的完整操作链 |
| 轮询刷新 | 知识库存在 `UPLOADING`/`PROCESSING` 条目时，前端每 4 秒自动刷新列表 |
| 二次确认 | 关键操作（重新向量化、发布新版本）弹出确认对话框，需用户显式确认 |
| 发布快照 | 发布时生成的不可变配置快照与递增版本号，历史版本不被修改 |

### 1.4 文档约定

- 用例编号规则：`TC-<模块>-[PR]-<序号>`，模块见第 4 章；`PR` 表示数字员工预览/发布模块。
- 用例步骤中的「点击」「输入」「选择」均指真实浏览器操作；涉及键盘操作会显式标注（如 Enter）。
- 「观察 Network」指打开浏览器开发者工具（F12）Network 面板核对对应请求/响应，仅作为页面结果的辅助佐证，不构成直接调接口行为。
- 测试数据字段用「」包围，示例数据见第 2.4 节与各用例「测试数据」栏。

## 2. 测试环境说明

### 2.1 软硬件环境

| 类别 | 配置要求 |
|---|---|
| 服务器 | 满足后端运行的最低配置；向量化任务依赖外部模型与向量库连通性 |
| 浏览器 | Chrome / Edge 最新稳定版（本项目兼容最近两个稳定大版本） |
| 分辨率 | 建议 ≥1440px 桌面分辨率；覆盖 1200–1440 / 768–1200 断点各抽验一次 |
| 测试机 | 可访问前端地址与后端接口地址，可操作浏览器开发者工具 |

### 2.2 部署拓扑与访问地址

```text
浏览器 ──> 前端管理后台（Vite dev :5173 / Nginx 静态产物）
                │  /api 反向代理
                └──> 后端服务（:8080）
                        │
                        ├── MySQL 8.0（业务数据）
                        ├── 向量数据库（Redis + RediSearch 或内存向量库）
                        └── 向量模型服务（qwen3.7-text-embedding 等，经 Spring AI 接入）
```

| 环境项 | 建议值 |
|---|---|
| 前端访问地址 | `http://localhost:5173`（开发模式，/api 反代到本地后端） |
| 后端服务地址 | `http://localhost:8080` |
| 后端配置来源 | 环境变量 / `.env`（含 bootstrap 管理员初始化参数与模型、向量库连接信息） |

> 说明：若后端启用了「本地向量模型 + 内存向量库」门控（`local` 配置），向量化在进程内完成，无需外部服务；若启用真实模型/向量库，则需保证其连通且额度可用。两种形态均不影响本测试用例的执行路径。

### 2.3 测试账号与初始化

| 账号 | 角色 | 来源 | 用途 |
|---|---|---|---|
| admin（示例：`harness-admin`） | ADMIN | 启动时按 `harness.bootstrap-admin.username/password` 幂等初始化创建 | 全部管理功能用例 |
| 普通用户（示例：`tester-user`） | USER | 环境初始化阶段一次性创建 | 权限边界用例（TC-SEC） |

说明：

- 管理后台前端无注册页面，注册与管理员初始化均为后端受控流程（`POST /api/auth/register` 固定创建 `USER` 角色；管理员由启动初始化创建）。因此本测试文档将「注册/初始化」作为**环境初始化步骤**执行，不进入页面级用例；其功能正确性通过「初始化账号可正常登录」间接验证（TC-REG-001）。
- 环境初始化（创建普通用户、预留测试数据）允许使用一次性初始化脚本执行，**该步骤不属于用例执行环节**；从用例 TC-AUTH-001 起，所有功能验证必须通过页面操作完成。

### 2.4 测试数据准备

| 数据类别 | 内容 |
|---|---|
| 知识库文件 A | `客服知识库.txt`，内容为客服问答语料，编码 UTF-8，< 1MB |
| 知识库文件 B | `产品手册.md`，内容为产品说明文档，< 1MB |
| 非法类型文件 | `图片.png`、`脚本.exe` |
| 超大文件 | `超限文档.txt`，构造 > 20MB |
| Skill 数据 | 名称「客服技能」、内容配置「你是客服助手……」（< 10000 字符） |
| 数字员工数据 | 名称「售后助手」、系统提示词「你是售后服务助手……」（< 20000 字符） |

预置条件（用例执行前须满足）：

1. 后端已启动，bootstrap 管理员账号初始化成功。
2. 已存在至少 2 个 `READY` 状态知识库（供 Skill 关联），可先用 TC-KB-007/008 上传后等待就绪。
3. 已存在至少 2 个已关联 READY 知识库的 Skill（供数字员工关联），可先用 TC-SK-005 创建。
4. 测试浏览器已清理缓存与 localStorage（保证无残留会话）。

## 3. 测试方法与约定

### 3.1 测试方法：全流程点击操作法

**核心原则：禁止直接调用后端接口进行功能验证。**

- 所有用例必须以真实用户的视角，通过浏览器页面上的输入、选择、点击、键盘操作完成整条业务链路。
- 用例中出现的「数据」「按钮」「提示」均以页面实际呈现为准；不允许绕过页面直接使用 Postman/curl 等工具发起业务请求来替代操作步骤。
- 允许观察浏览器 Network 面板中的请求与响应，用途仅限：核对页面行为对应的请求路径、参数、响应 `code`/`message`，辅助判断前后端契约是否一致。观察行为不作为功能操作手段。
- 后端数据的核对（如需确认写入结果）通过**页面列表/详情刷新展示**完成，不使用数据库直查替代页面断言。

### 3.2 验证手段

| 手段 | 说明 |
|---|---|
| 页面断言 | 断言元素展示、文案、状态、跳转路径、按钮可用性（含禁用/置灰） |
| 提示断言 | 断言 Toast / 内联错误 / 对话框文案与出现时机 |
| 请求断言 | Network 面板核对方法、路径、请求体与响应 `code`（辅助，非替代） |
| 截图留证 | 每用例关键步骤截图，作为实际结果附件 |

### 3.3 状态观察规则

- 知识库上传后状态可能经历 `UPLOADING → PROCESSING → READY`；处理中页面自动轮询（间隔 4 秒）。用例中等待就绪时，允许在页面停留观察轮询刷新结果，**禁止**通过重发请求或人工刷库加速。
- 数字员工发布结果以页面 Toast 与预览页版本展示为准。

### 3.4 结果判定

| 判定 | 定义 | 后续动作 |
|---|---|---|
| 通过 | 实际结果与预期完全一致 | 填写执行记录，继续下一用例 |
| 失败 | 实际结果与预期不一致（功能缺陷） | 按第 8 章登记缺陷并反馈 |
| 受阻 | 环境/前置条件不满足，无法执行 | 标注受阻原因，待条件满足后补测 |

- **优先级**：高（核心链路/影响主流程）、中（功能细节）、低（体验/边界兜底）。

- **操作步骤**：按顺序执行的浏览器操作，数字序号表示步骤次序。
- **预期结果**：每步或最终可验证的结果。
- **实际结果 / 备注**：执行时填写（见第 7 章）。

### 8.2 严重级别定义

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 致命 | 阻塞主流程或核心功能不可用，数据损坏 | 登录完全不可用、发布流程崩溃 |
| P1 严重 | 核心功能部分失效，但存在绕行路径 | 发布校验结果与按钮状态不一致、列表加载失败 |
| P2 一般 | 非核心功能缺陷，不影响主链路 | 计数显示不一致、文案不准确 |
| P3 轻微 | 体验/样式/文案细节问题 | 按钮间距、提示语措辞 |

### 8.3 缺陷处理流程

```text
测试发现缺陷
    │ 1. 登记缺陷表（编号 DEF-xxx、级别、复现步骤、截图）
    ▼
开发修复（P0/P1 当日反馈，P2/P3 按迭代排期）
    │ 2. 修复后同步缺陷状态为「待回归」
    ▼
回归验证（由测试执行：复现原用例步骤）
    │ 3. 通过 → 状态「已关闭」；不通过 → 退回开发
    ▼
关闭并归档（记录回归日期与结论）
```

### 8.4 反馈渠道与时效

1. 测试过程中发现缺陷立即填入 8.1 缺陷登记表，并通知开发（P0/P1 即时，P2/P3 当日汇总）。
2. 每轮测试结束后输出《执行汇总表》与缺陷清单，作为联调阶段周例会输入。
3. 缺陷回归须复用原用例编号与步骤，避免二次设计用例。
4. 阻塞类问题（环境、数据依赖）及时标注「受阻」并说明恢复条件。

## 9. 验收标准

全部满足以下条件视为系统测试通过：

1. 核心链路用例（标记优先级「高」）通过率 100%：登录、知识库上传就绪、Skill 创建、数字员工创建与发布、预览与版本展示、权限拒绝。
2. 整体通过率 ≥95%（按第 7.2 节口径），「创建数字员工」模块通过率 100%。
3. 无 P0 遗留缺陷；P1 缺陷 ≤2 且均有明确修复计划与回归结论。
4. 所有「失败/受阻」用例均有问题反馈与处理记录（第 8 章），受阻项具备恢复条件。
5. 前后端契约校验通过：页面操作对应的请求路径、参数、响应 `code` 与 [API 约定](./API_SPEC.md) 一致（含错误码映射文案展示正确）。
